# svgshaper Constitution

## Core Principles

### I. Чистая библиотечная архитектура

svgshaper MUST поставляться как библиотека с документированным публичным API.
Доменная логика MUST жить в библиотечном крейте и MUST NOT зависеть от бинарника,
UI, окна, GPU или игрового движка.

- Публичный контракт — это публичные типы и функции библиотеки. Внутренние модули
  MUST оставаться приватными, пока они не входят в этот контракт.
- Каждый публичный модуль MUST иметь одну ясную ответственность и MUST быть
  пригоден к использованию без необязательной интеграционной обвязки.
- Крейты и модули без собственной доменной задачи запрещены.
- Бинарные цели MAY существовать только как примеры или инструменты разработки.
  Они MUST NOT содержать доменную логику, которой нет в библиотеке.

Обоснование: библиотечное ядро встраивается в Bevy и в другие хосты и не тянет
за собой приложение.

### II. Rust как язык реализации

Весь производственный код svgshaper MUST быть написан на Rust.

- Публичный API MUST следовать идиомам Rust: владение и заимствование явны,
  отсутствие значения выражается через `Option`, восстановимый сбой — через
  `Result`.
- Библиотечный путь, который вызывающий код достигает корректными входными
  данными, MUST NOT завершаться паникой. Паника допустима только при нарушении
  внутреннего инварианта.
- `unsafe` MUST быть локализован, сопровождён инвариантом безопасности и покрыт
  тестом. Безопасный Rust обязателен там, где он выражает ту же семантику.
- Редакция Rust и MSRV MUST быть объявлены в манифесте крейта. Изменение MSRV
  MUST фиксироваться в описании изменения, которое его вводит.

Обоснование: единый язык и явные границы ошибок делают библиотеку предсказуемой
для встраивания.

### III. Базовые тесты обязательны

Каждое наблюдаемое публичное поведение MUST иметь базовый автоматизированный тест
до того, как изменение считается завершённым. Это требование обязательно.

- Базовый тест — это unit- или интеграционный тест, который вызывает публичный
  API и падает, если заявленное поведение удалено или изменено.
- Набор тестов ядра MUST запускаться командой `cargo test`.
- Тесты ядра MUST NOT требовать приложение Bevy, GPU, дисплей, сеть или внешние
  сервисы.
- Изменение наблюдаемого поведения MUST добавлять или обновлять тест, который
  ловит регрессию этого поведения.
- Публичная функция или тип без теста на заявленное поведение нарушают эту
  конституцию.
- Порядок «сначала тест, потом код» не требуется. Обязателен сам тест, а не цикл
  TDD.

Обоснование: обязательны базовые тесты на публичное поведение. Правило
проверяется тестом, который падает при регрессии, и зелёным `cargo test` без
внешнего окружения.

### IV. Асинхронное ядро

Операции с ожиданием, вводом-выводом или отменой MUST быть доступны как
асинхронный API: `async fn` либо асинхронный трейт с документированным
контрактом.

- Публичные типы ядра MUST NOT зависеть от конкретного исполнителя (`tokio`,
  `async-std`, исполнитель Bevy или иной runtime). Вызывающий код, включая
  плагин Bevy, предоставляет исполнитель.
- Асинхронный путь библиотеки MUST NOT блокировать поток вызывающего кода.
- Синхронный API MUST ограничиваться чистыми вычислениями без ввода-вывода и
  без ожидания.
- Отмена и ошибки ожидания MUST быть видны вызывающему коду через контракт
  `Future` и `Result`, а не через скрытое состояние.

Обоснование: ядро без привязки к runtime исполняется и в Bevy, и вне его и не
блокирует кадр или рабочий поток хоста.

### V. Интеграция в Bevy как плагин

Интеграция с Bevy MUST быть необязательным плагином (`bevy::app::Plugin`) поверх
библиотеки. Библиотекой MUST быть можно пользоваться, не подключая плагин и не
включая зависимость Bevy.

- Зависимость Bevy MUST быть выключена по умолчанию и включаться отдельной
  Cargo-feature.
- Плагин MUST быть тонким адаптером: он ставит работу в расписание Bevy,
  отображает типы библиотеки на ресурсы, события и компоненты и MUST NOT
  заново реализовывать доменную логику.
- Подключение в хост-приложение MUST сводиться к одному вызову `add_plugins`
  и к настройке ресурсов Bevy. Скрытая инициализация при импорте запрещена.
- Доменные типы ядра MUST NOT ссылаться на типы Bevy.
- Плагин MAY жить в том же крейте за feature либо в отдельном крейте. Направление
  зависимости одно: плагин зависит от ядра, ядро от плагина не зависит.

Обоснование: удобство интеграции означает, что хост добавляет один плагин, а
пользователь без Bevy эту зависимость не получает.

## Technology Constraints

- Продукт — библиотечный крейт Rust. Обязательного бинарника нет.
- Асинхронное ядро строится на `std::future` и не выбирает runtime за
  вызывающего.
- Bevy подключается только через необязательную feature. Конфигурация по
  умолчанию MUST собираться и тестироваться без Bevy.
- Публичный API MUST быть задокументирован так, чтобы вызывающий код мог
  использовать его без чтения внутренних модулей.
- Примеры и инструменты MUST оставаться вне доменного контракта.

## Quality Gates

Изменение не считается готовым, пока не выполнены все пункты:

- `cargo test` для конфигурации ядра (без feature Bevy) завершается успешно.
- Новое или изменённое публичное поведение имеет базовый тест по принципу III.
- Если изменение затрагивает плагин Bevy, вместе с ним есть тест адаптера. Тест
  проверяет регистрацию плагина и связь с API ядра и не требует окна или GPU.
- Ревью MUST сверять изменение с принципами I–V. Отступление от принципа
  допустимо только как записанная поправка конституции.
- Доменная логика, которая есть только в бинарнике, примере или плагине,
  является основанием отклонить изменение.

## Governance

Эта конституция главнее конфликтующих практик, шаблонов и локальных
договорённостей. Если спецификация, план или реализация расходятся с
конституцией, правка вносится в спецификацию или код.

Порядок поправок:

- Поправка описывает, какой принцип меняется и почему.
- Версия конституции обновляется по правилам ниже. Дата `Last Amended`
  ставится в день принятия поправки.
- Удаление или переопределение принципа, которое ломает уже принятые
  спецификации, требует краткого плана миграции этих спецификаций.

Политика версий (семантическое версионирование):

- MAJOR: обратно несовместимое удаление или переопределение принципа.
- MINOR: новый принцип или существенное расширение существующего.
- PATCH: уточнение формулировки без смены смысла.

Проверка соответствия:

- Каждый план и каждый набор задач MUST указывать принципы, которым он следует.
- Ревью MUST подтвердить принципы I–V и ворота качества до принятия изменения.
- Усложнение публичного API или зависимостей MUST быть оправдано одним из
  принципов этой конституции. Неоправданная сложность отклоняется.
